# Y2E-165 — Resolve the wheel and select-button event path

Canonical issue [#24](https://github.com/SchulzCode/Y2Linux/issues/24);
[execution order](../next-five-platform-foundations.md).

## Type and goal

**Research.** Specify the minimal path for clockwise/counterclockwise wheel
movement and the select button to become Linux evdev events.

## Why it comes next

Local controls are the next useful interaction primitive once diagnostics work.
Power/transport evidence should precede controller access. Existing `mtk-kpd`,
`mtk-tpd` and APT32F/UPDATE names do not prove which hardware produces the wheel.

## Dependencies

Execute after Y2E-160; use its supply/transport findings and report unresolved
prerequisites instead of assuming them. Read `display-input.md`, the retained
input capability inventory and Android behavior reference. No RAM expansion or
full display driver is required for this research.

## Exact scope

- Map only wheel CW/CCW and select press/release through retained stock input
  capabilities, keylayout and the exact corresponding FM handler/call sites.
- If safe stock access and owner actions are available in the later session,
  capture bounded passive evdev/getevent output for those actions. No synthetic
  input, device grab, firmware update or arbitrary vendor ioctl. Otherwise state
  the missing event observation and preserve the offline findings.
- Resolve transport, IRQ, pinmux/reset/supply prerequisites only for this path;
  distinguish an MCU protocol from GPIO/keypad behavior using evidence.
- Specify event codes, direction, release/repeat semantics and the smallest
  upstream-compatible driver/DT addition, with raw trace fixtures where available.

## Explicit out-of-scope

Implementing input, all-button coverage, power-key hold/off, wake/suspend,
Bluetooth/AVRCP, app navigation/acceleration policy, MCU firmware and bus probing.

## Expected files/components

`docs/knowledge/display-input.md`, a focused `docs/knowledge/input-path.md`,
`open-unknowns.md`; reviewed prospective Linux input/evdev component and DT nodes.
Android keylayout/handler references are evidence, not copied application code.

## Acceptance criteria

CW, CCW and select each have a source/event mapping, or explicitly named missing
observation. No Android KEYCODE is substituted for an unproven evdev code. The
selected path has register/protocol, supply, IRQ and pinmux provenance adequate
for one implementation, or a single bounded prerequisite is reported. Draft the
future on-screen event-counter test and stop criteria; no driver is authored.

## Validation

Cross-check sample press/release/detent ordering against stock handler behavior;
check proposed v6.18 input API/binding support from pinned source. Count exact
observed actions without claiming unmeasured debounce or acceleration behavior.

## Stop conditions

Ambiguous wheel source, unknown MCU protocol or required privileged/bus-changing
access stops implementation specification. Do not guess GPIOs, scan addresses or
flash peripheral firmware to discover functionality.

## Unlocks next

A tiny evdev input implementation and local navigation of future diagnostics.
Display research follows in the queue without requiring that driver to be built.

## Session and execution boundary

Planning only today. Executing this research issue later does not authorize a
Linux build, DTS/driver change, flash, new boot, bus scan, raw MMIO access,
security change or partition write. Use retained evidence and pinned v6.18 source
first; allow only explicitly safe, bounded stock observations when available.
Keep private device data in ignored evidence storage and cite source/hash/offset
locators in knowledge documents. Preserve uncertainty; do not invent a compatible,
register value or board wire. Do not create follow-on issues automatically.

Future localized implementation uses one clean build, affected tests and the
D08/layout/BOOTIMG validator plus final size/hash. Material memory/architecture/
packaging changes or a new hardware subsystem require the broader relevant
verification boundary, not a habitual full provenance/recovery re-audit.
Stock preloader/LK, partition layout and calibration remain protected.
